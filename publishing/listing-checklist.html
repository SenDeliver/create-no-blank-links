Modrinth steps

  1. modrinth.com → sign in with GitHub → Create project → type Mod.
  2. Fill the shared metadata table. Description = paste publishing/modrinth-description.md.
  3. Upload icon + gallery images.
  4. Versions → Create version: jar, number 1.0.0, Release, NeoForge, 1.21.1, dependency Create required, changelog from release notes.
  5. Submit for review. First review takes 1 to 3 days. Project URL becomes modrinth.com/mod/no-blank-links.
  6. Settings → create a PAT with "Create versions" scope → GitHub repo secret MODRINTH_TOKEN. Until the project is approved, leave the secret unset: the workflow then skips Modrinth.

CurseForge steps

  1. curseforge.com → Authors → Start a project → Minecraft → Mods.
  2. Name, slug no-blank-links, summary, categories, license MIT, icon icon-400.png.
  3. Description: switch editor to Source/HTML and paste publishing/curseforge-description.html.
  4. Upload file: jar, display name No Blank Links 1.0.0, Release, 1.21.1 + NeoForge + Java 21, relation Create required.
  5. Submit. Note the numeric Project ID from the project page sidebar.
  6. API tokens page → create token → GitHub secrets CURSEFORGE_TOKEN and CURSEFORGE_PROJECT_ID.

After listing: releases are automatic

.github/workflows/publish.yml runs on every GitHub Release: builds the jar, attaches it to the GitHub release and, when the secrets exist, uploads it to CurseForge and Modrinth. Without secrets it only attaches the jar and prints a notice; it never fails for a missing token. Changelog: publishing/release-notes-<version>.md if it exists, else the ## [x.y.z] section of CHANGELOG.md. A release that already carries the jar (attached by hand) keeps that asset. A manual run (Actions → Publish → tag) publishes the CI build to the sites but never replaces the GitHub asset. For 1.0.0 the CI build differs from the deployed jar (logo added after the deploy), so upload 1.0.0 by hand on both sites from the GitHub release asset; do not run the workflow for it.

git tag v1.0.1 && git push origin main v1.0.1
gh release create v1.0.1 --title "No Blank Links 1.0.1" --notes-file publishing/release-notes-1.0.1.md

Jar naming

1.0.0 ships as noblanklinks-1.0.0.jar (already on the server, unchanged). From 1.0.1 the jar can adopt the Octo Arms scheme no-blank-links-<version>+mc1.21.1.jar (set archivesName in build.gradle); the workflow picks up whatever build/libs/ contains. Tags may be v1.0.1 or v1.0.1+mc1.21.1.
